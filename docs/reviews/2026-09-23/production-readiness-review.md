# Stride production-readiness review

Reviewed 23 September 2026 against the current working tree and the local browser preview. No production application code, saved plan, connection, payment or provider data was changed. The local preview was started for inspection.

## Release assessment

Stride is a web training planner and running journal with workout export and an Intervals.icu-to-Garmin delivery path. It has no phone recording runtime. A public paid release is not ready: there are reproduced correctness defects, no durable offline journal, deliberately disabled billing, and unfinished production identity/privacy verification. A phone-recording launch additionally requires a substantial native subsystem.

This is not a finding that an existing GPS implementation drains batteries or loses routes: that implementation does not exist. No field GPS, battery, physical-watch, VoiceOver/TalkBack, production ingress or production load measurements were performed. Existing unit tests passing does not establish those properties.

Evidence classifications: **reproduced** means an isolated test demonstrated the behavior; **confirmed** means source or browser inspection establishes it; **unverified** means a deployment/performance claim still needs measurement. P1 denotes serious current reliability/correctness defects. P2 denotes material usability or hardening work. Recording and paid-launch prerequisites are identified separately.

## Current-product priorities

| The Issue | The Impact | The Fix |
| --- | --- | --- |
| **P1 · Workout-count controls contradict the engine — reproduced.** A finish-intent 10K profile with an explicit two-workout choice renders selected **0 / All easy**, while the engine resolves two. Automatic mode also displays zero when the engine resolves one. Choosing a positive value changes intent to improve. [UI policy](../../../components/training-controls.tsx#L92), [engine policy](../../../lib/training-structure.ts#L64). | The user cannot trust the controls or faithfully edit a finish-oriented plan with controlled workouts. This explains disappearing options even when generated prescriptions pass tests. Merely opening the form was not shown to delete workouts. | Use one shared resolved frequency model across engine, controls, previews and saved summaries. Preserve intent independently. Expose automatic as an actual selectable mode. Browser-test generate → preferences → preview → save → reopen for automatic and 0/1/2 across all named distances and both intents. |
| **P1 · Contradictory zones accepted — reproduced.** Easy HR 200–220 bpm with interval HR 80–90, and easy pace 3:00–3:10/km with interval pace 10:00–10:20/km pass validation. [Validator](../../../lib/workout-targets.ts#L57). | Individually valid fields create an incoherent training prescription that can be exported to a watch. | Validate cross-band ordering with sensible overlap, show an ordered zone review, retain method/source/review date and test the exported result. Do not turn age-based estimated maximum HR into assumed measured physiology. |
| **P1 · A lost response can cause duplicate manual runs — reproduced.** With no active plan, two identical free-run API requests both return 200 and create two different IDs, even when the input supplies one stable run ID. [Route](../../../app/api/plan/route.ts#L87), [storage](../../../lib/standalone-runs.ts#L23). | A successful save followed by a Wi-Fi/cellular interruption can become two runs after a retry, inflating history and later training evidence. | Persist an account/epoch-scoped mutation UUID before submission. Atomically store request hash, original result and run under a unique key. Same ID/body returns the original result; changed body under the same ID conflicts. Test commit-then-response-loss, concurrent retry and retry after restart. |
| **P1 · Offline cold launch and writes are unsupported — confirmed.** Current plan state is in React memory; requests use no-store. No service worker, durable plan cache or mutation outbox exists. [Client](../../../lib/client-api.ts#L74), [state hook](../../../components/app/use-training-plan.ts#L52). | A browser restart at a remote start line can remove access to the planned session. Feedback cannot reliably be saved at an offline finish. | Cache the web shell and account-scoped upcoming-workout snapshots in IndexedDB. Write commands transactionally to an outbox before acknowledging local persistence. Distinguish Saved on device, Waiting to sync and Synced. Replay stable IDs with authentication and revision checks; handle quota, eviction and account changes. Test airplane-mode cold launch and reconnect conflicts. |
| **P1 · Unsaved run feedback is not durable — confirmed.** Extra-run fields use component state; onboarding alone persists a session-storage draft. [Form](../../../components/training/use-extra-run-form.ts#L33). | Refreshing to repair connectivity, closing a tab or OS eviction loses the runner's entries. “Your input is still here” only holds while that form survives. | Persist scoped drafts with a bounded debounce and on blur. Recover explicitly; clear only after verified save or discard. Draft persistence and queued mutations must be separate. |
| **P1 · Impossible activity summaries pass cross-field validation — reproduced.** Exactly 100 km in two seconds is rejected by the minimum-duration rule, but **100 km in one or two minutes is accepted**. [Run input](../../../lib/run-input.ts#L5), [provider normalization](../../../lib/provider-activities.ts#L11). | Bad imports or typos can contaminate load and readiness calculations without failing single-field bounds. | Add sport-aware plausibility checks and a review/quarantine state. Preserve raw source facts, exclude suspect records from adaptation, and explain the conflict. Never silently clip an impossible value into a plausible one. |
| **Public-release gate · Identity depends on an unverified hosting boundary.** The application trusts `oai-authenticated-user-id`. A deployment gateway may correctly supply it, but unit tests do not prove stripping of caller-supplied headers or blocked direct origins. [Identity](../../../lib/server.ts#L33). **No bypass was attempted or demonstrated.** | All otherwise careful owner-scoped storage depends on this boundary. | Verify the actual deployed gateway, every API route, direct-origin protection, expiry/logout and two-account isolation. Outside that trusted gateway, verify signed sessions server-side and derive identity from the verified subject. Preserve account epochs and origin checks. |
| **Public-release gate · Privacy/support operations are explicitly unfinished.** The current privacy page identifies missing operator/contact/retention/backup-erasure commitments. [Notice](../../../app/privacy/page.tsx#L8). | Public users have no established operational path for sensitive-data questions, restore failures or incidents. | Finish operator notice, retention/deletion inventory, downstream-copy explanation, customer support ownership and incident/restore drills. Obtain appropriate review for the actual launch jurisdictions. Application-row deletion is not proof of removal from provider devices or infrastructure backups. |
| **P2 · Target settings silently replace automatic benchmark mode — reproduced path.** Absent target settings mean benchmark-derived pace in the engine, but the form initializes them as Effort. Saving that apparent current selection disables automatic pace targets. There is no automatic reset option. [Form](../../../components/workout-target-settings.tsx#L38), [target resolution](../../../lib/workout-targets.ts#L166). | A runner can unintentionally change training targets while believing they are preserving them. | Make automatic benchmark, manual pace, manual HR and effort explicit modes. Show derived values and their origin. Treat an unchanged save as a no-op; offer reset to automatic and include target changes in review diffs. |
| **P2 · Pace precision exceeds demonstrated confidence.** Riegel is implemented explicitly; training bands are additional heuristics. The exported pace tolerance is approximately ±5 seconds/km, while steady uses the tempo estimate. [Pacing](../../../lib/fitness-pacing.ts#L125). | A narrow watch alert can encourage chasing an estimate that is inappropriate for conditions or an old/incomparable benchmark. “Steady and comfortable” may not match the prescribed tempo target. | Separate race prediction, coaching target and alert tolerance. Show benchmark date/course and extrapolation limits, retain an effort fallback, review the steady mapping with a qualified running coach, and test representative prescriptions outdoors. Do not present passing arithmetic tests as validation of coaching outcomes. |

## Recording, GPS, battery and execution prerequisites

| The Issue | The Impact | The Fix |
| --- | --- | --- |
| **Recording blocker · No native run session or GPS pipeline.** No location APIs, Kalman filter, sensor stream, live run timer, map or recording state machine exists. | Stride cannot currently start, record and finish the phone-only marathon described in the request. | Build a persisted native session service, independent of navigation: idle → acquiring → running ↔ paused → finishing → saved/recoverable. Use supported iOS Core Location background activity/session APIs and an Android location foreground service. A background web interval is not a substitute. [Apple](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background), [Android](https://developer.android.com/develop/background-work/services/fgs). |
| **Recording blocker · No route-quality policy.** Kalman smoothing is absent, but adding it alone would not prove accurate distance. | Urban reflections, stale points and signal loss can create false speed, distance and automatic pauses if a recorder is added without quality handling. | Preserve raw coordinates, accuracy, source time and processed results. Reject stale/non-monotonic points; flag implausible jumps using uncertainty and speed/acceleration. Mark gaps instead of drawing fabricated exact tracks. Evaluate an uncertainty-aware filter on recorded routes with tight corners, trees, tunnels and stoplights; keep elapsed time independent of GPS. |
| **Recording blocker · No active-session crash checkpoint.** Existing backups restore journals, not an in-progress workout. | An OOM at kilometre 15 has no Stride recording state to recover. A future recorder built only in React state would lose its session. | Persist append-only local SQLite sample/event chunks, session UUID, sequence numbers, time anchors, pause events, step position and upload watermarks. Checkpoint at an explicitly tested loss bound. Recover committed events after restart, show any unobserved gap, and distinguish OS termination from deliberate force-quit. Do not promise uninterrupted collection or recovery of samples never observed. |
| **Recording blocker · Interval execution, cue timing and auto-pause are absent.** Current steps are prescriptions handed to the watch. | There is no phone timing, transition, audio or pause accuracy to certify. | Drive transitions from monotonic elapsed time and validated distance thresholds, not accumulated UI timer ticks. Persist transition IDs; deliver cues once; define audio focus, music ducking, interruption and headset behavior. Auto-pause needs a configurable hysteresis/debounce policy, a manual override and a degraded-GPS fallback. Test resume, manual lap, skipped step and restart at each boundary. |
| **Recording blocker · In-run legibility and feedback have no dedicated screen.** The current workout is a scrollable instruction modal. | It is unsuitable as the primary interaction surface while sprinting, sweating or reading in sunlight. | Design a separate glanceable run screen: current interval, large elapsed time/distance/pace, next step and one dominant pause control. Prefer tabular numerals, 48–56-unit primary controls and optional screen lock. Add distinguishable split/pause/finish haptics with opt-out; avoid accidental finish and destructive gestures. Test real sunlight, rain, gloves and motion. These sizes are product targets, not a claim of a universal WCAG minimum. |
| **P2 · Battery and sensor budgets are unmeasured.** The existing app has no GPS/accelerometer/gyro sampling. Minor 15-second day-rollover timers remain active in source. | No honest battery-drain percentage can be supplied. A future recorder could waste energy on redundant sensors, network calls and map draws. | Use fused platform location; tune accuracy, sampling, batching and render frequency by session state. Activate motion sensors only for a justified feature. Batch local writes and defer uploads, avoid unnecessary wake locks, pause irrelevant hidden-page timers and stop sensors at finish. Measure 2/4/6-hour runs with locked screen, music, weak GPS, low power and representative devices. [Android battery guidance](https://developer.android.com/develop/sensors-and-location/location/battery). |
| **Recording gate · Sensitive permission flows are absent.** Stride currently does not request Location Always, motion, health-store or notification access. | Adding all prompts to onboarding would cause avoidable refusals and prevent users understanding the benefit. | Explain and request the minimum permission at first use. Do not universally require Always location for a workout started in the foreground. Handle denied, approximate, revoked and restricted states separately. Keep manual training/logging usable; let users continue without notifications and reconnect optional health access later. Apple and Android background behavior must be validated on supported versions. |

## Integrations, storage and API architecture

| The Issue | The Impact | The Fix |
| --- | --- | --- |
| **P1 · The journal is one growing JSON document with whole-document revisions.** Each edit saves the full state; the journal has a 1.5 MB application ceiling and revisions are unbounded. [Save path](../../../lib/server.ts#L194), [schema](../../../db/schema.ts#L8). | Small edits repeatedly copy old runs and notes. A sufficiently long-lived journal eventually refuses another valid save. Historical storage can grow well beyond the current-document limit. | Separate activities, feedback, blocks and revisions; return record-level mutations and paginated/delta reads. Keep bounded undo snapshots plus compact audit events and test restore after compaction. Do not add sensor samples to the plan blob. |
| **Recording blocker · No time-series data model.** There are no activity sample chunks, lap records, pause events, heart-rate streams or elevation series. | Fast incremental writes, recovery and post-run analysis cannot be implemented with the present summary-only schema. | Use local append-only chunks with checksums and sequence IDs; store server manifests and summaries in indexed tables, dense sample objects separately, and derived metrics with calculation versions. Preserve raw versus processed values. Index owner/start time and canonical activity/source identity; never index every sample as a giant plan revision. |
| **P2 · Serialization is not the primary bottleneck.** Measured synthetic 12-week plans are 33,403 and 88,886 bytes of compact JSON; local gzip estimates are 3,224 and 6,476 bytes. These are fixtures, not measured production transfers. | Replacing JSON with Protobuf prematurely adds complexity without fixing whole-state reads/writes. High-frequency traces would be a different workload. | First paginate, return deltas, enable appropriate transport compression and measure real transfer sizes. For future dense traces, benchmark packed binary/Protobuf or delta encoding in resumable chunks with checksums and upload acknowledgements. Keep small metadata APIs straightforward. |
| **P1 · Provider sends lack durable background jobs.** There are request timeouts and strong ambiguous-POST safeguards, but no durable worker guaranteeing completion after the caller disappears. | Wi-Fi → 5G → 3G can leave the runner uncertain and requiring manual reconciliation. Closing the app does not guarantee a pending send resumes. | Persist jobs and return operation IDs quickly. Use bounded workers, per-provider/account concurrency, retry classification, exponential backoff/jitter and dead-letter review. Preserve existing provider readback and avoid blindly resending an uncertain POST. Show queued, provider-received and device-confirmed as distinct states. |
| **P1 · Weekend-scale capacity is unverified.** One D1 binding handles all tenants; full snapshots, revision writes and database-backed rate limits amplify work. | A synchronized finish-time burst could queue writes and provider requests. No benchmark establishes when saturation occurs. | Load-test realistic journal sizes and finish bursts; measure p50/p95/p99 latency, errors, queue age and provider quotas. Keep API commits short and bound worker concurrency. Optimize/partition only after measurement. D1 documents serial query execution per database and overload behavior. [Cloudflare](https://developers.cloudflare.com/d1/platform/limits/). |
| **Ecosystem gap · HealthKit, Health Connect, direct Strava and direct Garmin adapters are absent.** The actual path uses an Intervals.icu API key and bridge. | Mainstream users need another service and developer-key setup; there is no direct phone health-store integration. | Add native HealthKit and Health Connect adapters with minimal scopes, persistent anchors/change tokens, source IDs and deletion handling. Add approved provider authorization and serialize token refresh. Garmin access requires application/review; do not market planned access as available. [Health Connect](https://developer.android.com/health-and-fitness/health-connect/sync-data), [Garmin](https://developer.garmin.com/gc-developer-program/program-faq/). |
| **P1 · Imported updates/deletions and cross-provider duplicates are not modeled.** Current deduplication protects scoped Intervals IDs, but there are no upstream versions/tombstones or canonical multi-source activity links. | A corrected source run stays stale; future watch/health/Strava copies could count several times. | Separate canonical activity from provider links, storing source version/hash, cursors and tombstones. Preserve user edits separately; match uncertain duplicates for review. Process revocation/privacy/deletion changes according to the provider and user's consent. Strava webhooks expose activity updates/deletion and deauthorization. [Strava](https://developers.strava.com/docs/webhooks/). |
| **P1 · Original activity timestamp and zone are lost.** The importer reads UTC/local start and timezone but persists date/summary only. [Normalization](../../../lib/provider-activities.ts#L31), [save](../../../app/api/plan/route.ts#L509). | A flight does not shift the existing date-only labels, but original instants, DST offsets and same-day chronology cannot be reconstructed. | Preserve UTC start/end, original IANA zone/offset and activity-local date. Default history to original local time; optionally show current-zone time. Keep plan dates as calendar dates. Test date-line travel, DST gaps/folds and doubles. |
| **Future sharing gate · No route-redaction layer.** No coordinates/public route sharing exist now; no current home-location leak was demonstrated. | A later route-sharing implementation could reveal home locations through maps, thumbnails, APIs or exports. | Keep raw routes private and generate separate redacted public geometry. Clip start/end regions and later passages through privacy zones; apply consistently to every share/export surface and preview the audience/result. A single deleted endpoint is insufficient. |
| **P2 · Hardening and diagnosis are incomplete.** CSP is minimal, credential envelopes lack key-version metadata, and errors omit useful safe operation categories/latency. | Defense in depth, key rotation and incident triage are weaker than a public subscription product needs. | Verify deployed headers; introduce framing protection and nonce/hash CSP carefully. Version encrypted envelopes and support controlled rotation. Add redacted operation metrics, queue/retry/provider outcomes and alerts without logging notes, credentials or coordinates. Preserve existing AES-GCM encryption, owner scoping and account/version fences. |

## Mobile UX and accessibility

| The Issue | The Impact | The Fix |
| --- | --- | --- |
| **P2 · Your Plan prioritizes settings over the schedule — observed.** At 390×844, the first screen contains the update banner, heading/actions and routine summary; no daily run appears. At 320×568, even the routine card extends below the fold. | Returning runners must scroll before answering “What am I doing this week?” Print receives scarce primary space. | Put current week and daily runs first; collapse the routine summary into a compact persistent chip/disclosure. Put Print/exports in overflow. Preserve one clearly named schedule-adjustment action. |
| **P2 · Logging is below optional explanation — observed.** The easy-workout dialog's Log this run button starts around y=923 at 390×844, after multiple supporting sections. | The core post-run action requires scrolling through content the runner may already know. | Add a safe-area-aware sticky action footer for logging/watch delivery as appropriate to state. Keep optional rationale secondary. Do not confuse Log run with Start recording. |
| **P2 · Date-rail traversal is noisy — confirmed.** The 23-week plan exposes 161 day controls before the workout in the accessibility tree. There is correctly only one keyboard Tab stop via roving tabindex. | Screen-reader browse/swipe navigation still encounters a large sequence. | Page the strip to 7–14 days, add previous/next and a full date picker, plus Skip to workout. Test actual VoiceOver/TalkBack traversal, not only keyboard focus. |
| **P2 · Touch/legibility polish is incomplete, not a blanket contrast failure.** Observed navigation is 46 px high, profile 44 px, Print/Adjust 40 px with ~12.3 px text, and dialog Close 38 px. No horizontal page overflow at 320 or 390 px. Dark-mode text was generally readable; sunlight was not tested. | Small secondary controls and dense text are less forgiving with motion, sweat and low vision. | Make ordinary interactive targets consistently generous; use larger in-run controls and scalable text. Validate light/dark contrast numerically, zoom/reflow and device text size. WCAG AA target minimum is 24 CSS px with exceptions, not a universal 44 px rule; normal-text contrast is 4.5:1. [Targets](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). |
| **P2 · Onboarding hides meaningful availability.** Defaults allow 120 weekday and 300 long-run minutes; actual limits live in advanced options. Benchmark fields recur in setup/customization. | A numerically feasible plan may be impossible in the runner's real week. | Ask weekday/long-day availability in the main flow and confirm time needed to preserve the declared baseline. Consolidate optional benchmark input, keep progressive disclosure for genuine expert options, and explain timezone behavior. |
| **P2 · Watch setup is too technical for broad acquisition.** It requires another account, an API key, external Garmin setup and on-device confirmation. HR targets use manual FIT fallback. | Users can abandon after creating a plan, before the product delivers practical value. | Check device/target compatibility early. Provide a guided first-workout handoff with explicit checkpoints and a tested model/firmware matrix. Offer approved direct authorization when available. Measure first-workout delivery and completion, not merely account creation. |
| **P2 · Routine operations use a blocking global modal.** [Progress screen](../../../components/action-progress.tsx#L35). Lazy dialogs also first show a generic opening screen. | Slow reads can trap navigation, produce visual flashes and duplicate announcements. | Use inline/local skeletons and one status announcement for routine reads; delay fleeting indicators, reserve blocking for truly atomic changes and offer clear retry/cancel where safe. Persist drafts before any recovery action. |
| **P2/P3 · Performance and assistive-technology quality lack release evidence.** A broad context distributes the entire app object, and no map/stats/music runtime exists to benchmark. There was no native screen-reader or maximum-journal mobile performance run. | Source structure suggests broad rerenders, but measured visual lag cannot be asserted. Passing static markup tests misses focus, gestures and announcements. | Profile on representative phones with maximum supported history. Split state or selector subscriptions where measurements justify it; keep future sensor updates outside the planning tree. Add browser journey/a11y checks and device tests. For live metrics, announce on demand or controlled milestones rather than every sample over coaching audio. |

No operational paywall, entitlement store, native purchases or customer portal exists. [Billing route](../../../app/api/billing/route.ts#L7). | There is no functioning paid lifecycle or paywall load time to evaluate. ## Requested failure scenarios

| The Issue | The Impact | The Fix / acceptance test |
| --- | --- | --- |
| OS kills the app at kilometre 15. | No Stride phone run currently exists to recover; journal backup is unrelated. Unsaved form state can be lost today. | For recording, kill during running/pause/interval transition/chunk commit/upload. Relaunch from committed local events with an explicit gap, stable run ID, correct pause/time semantics and no duplicated final activity. |
| A complete marathon has no cellular coverage. | Stride cannot record it. A previously delivered watch workout may work offline on that device, which remains device-specific. The web journal cannot cold-launch reliably or save offline. | Airplane-mode cold start, full local record/save, app restart, then reconnect. The final server record must equal the saved local activity once, with resumable checksummed uploads and independent plan access. |
| Flight changes timezone. | Existing calendar-day labels remain stable, but imported original instant/zone is discarded. | Test original local display, explicit current-zone display, date-line crossing and DST using persisted instants/zones. Do not auto-shift scheduled plan dates. |
| Wi-Fi → 5G → 3G during sync. | A 25-second client timeout may hide a completed write; manual free-run retry can duplicate it. Provider delivery already treats uncertain POST results carefully. | Inject loss before send, after server commit and during response. Reopen and replay the same durable mutation/job; verify one result, coherent status and no blind provider duplicate. |
| GPS reports 100 km in two seconds. | No GPS ingestion exists; the manual exact value is rejected, but nearby absurd summaries pass. | Reject/quarantine cross-field and stream anomalies before adaptation. Retain source and reason; test timestamp disorder, duplicate points, huge jumps and real GPS gaps. |
| Subscription renews/fails while offline. | No production subscription lifecycle exists. | Exercise trial conversion, grace, account hold, cancellation, refund, revoked purchase and restore under delayed/duplicate notifications. Preserve eligible cached access within policy and never cancel an active recording. |

## Evidence, limits and release gates

- Existing focused suites passed: 131 backend/import/recovery/delivery/date tests, 45 billing/session/loading/recovery tests, and 47 target/benchmark/watch/readback tests. These groups overlap; they are not a unique-test total. The reproduced defects demonstrate gaps in those suites.
- Source inspection and isolated React rendering proved the frequency discrepancy; pure-function probes proved target inversion and implausible summary acceptance; the actual API with in-memory SQLite proved duplicate manual creation.
- Browser inspected Today, Plan, Settings, workout detail and event change at 390×844 and narrow navigation at 320×568. Restored the original viewport. No plan change, run log, connection or purchase was submitted. Browser emulation is not outdoor or physical-device validation.
- Before a public planner release: close the current P1 defects, demonstrate durable offline plans/feedback, verify deployed identity and account isolation, complete support/privacy/restore operations and pass real browser/mobile accessibility journeys.
- Before a paid release: implement and sandbox-test the complete entitlement lifecycle and recovery/support path.
- Before advertising phone recording: pass native background/kill/offline/GPS/audio/battery field tests, implement private raw streams and consistent share redaction, and verify device-specific behavior.

Detailed companion evidence: [backend and sync](backend-sync-audit.md), [billing and offline](billing-offline-audit.md), [workout targets and UX](workout-ux-audit.md). Current approved marathon progression was not changed by this audit.
