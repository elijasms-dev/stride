# Offline, recording, battery and billing audit

Reviewed 23 September 2026. This is a source audit with isolated, synthetic tests. No real account, payment, provider recording or live journal was changed. No device battery, GPS accuracy, background survival or purchase conversion measurements were made.

Stride currently implements a web training planner and journal with watch workout export/delivery. It does not implement a phone run recorder. Native recording requirements below are missing capabilities relative to the requested product ambition, not claims that an existing recorder is malfunctioning. Billing is deliberately disabled, so missing commercial infrastructure is a paid-launch blocker rather than an exploitable live paywall.

P1 means a material integrity/reliability defect or a blocker before launching the corresponding advertised capability. P2 means a significant follow-up after the basic capability works.

| The Issue | The Impact | The Fix |
| --- | --- | --- |
| **P1 — Retrying a manual run can create a duplicate. Confirmed with the actual API in an in-memory database.** The no-plan `freeRun` branch runs before the plan-version guard. `saveStandaloneRun` replaces even a client-supplied stable ID with a new UUID. Identical sequential requests both return 200 and create two runs. Evidence: [route.ts:87](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/app/api/plan/route.ts:87), [standalone-runs.ts:23](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/lib/standalone-runs.ts:23). | A Wi-Fi/cellular handover can hide a successful response. Retrying then counts one run twice, inflating journal totals and the history later used to generate a plan. Account revision checks prevent simultaneous stale writers but do not make sequential retries idempotent. | Generate a durable `mutationId` before first submission. Scope it to account ID and epoch, persist a request hash and result under a unique constraint, and commit it atomically with the run. Return the original result for the same ID/body; reject the same ID with a different body. Do this for all creating mutations, not only plan activation. Add commit-then-response-loss and retry-after-reload tests. |
| **P1 — Offline access exists only while the current page remains alive.** Plan/account/import state is held in React memory. Reads explicitly use `cache: 'no-store'`. There is no service worker, IndexedDB cache, offline app shell or durable write outbox in the source tree. Evidence: [use-training-plan.ts:52](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/components/app/use-training-plan.ts:52), [client-api.ts:80](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/lib/client-api.ts:80). The UI correctly says to reconnect before saving at [app-notices.tsx:93](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/components/app/app-notices.tsx:93). | A runner can lose access to the workout after a browser/OS restart in a low-signal start area. They cannot depend on saving feedback at the finish. A printable export is useful but does not provide an offline journal. | For the web planner, cache the application shell and explicitly persist a versioned, account-scoped upcoming-workout snapshot in IndexedDB. Store pending feedback in a transactional outbox before showing “Saved on this device.” Show separate local/sync states and last successful sync time. On reconnect, replay idempotent commands, refresh authentication and present conflicts instead of overwriting a newer plan. Clear/isolate data on account change; handle schema migration, quota/eviction and logout. Test cold launch in airplane mode. |
| **P1 — Unsaved run feedback has weaker recovery than onboarding.** Extra-run date, minutes, distance, effort, feeling and note are only `useState` values. Onboarding at least saves an account-scoped draft to `sessionStorage`. Evidence: [use-extra-run-form.ts:33](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/components/training/use-extra-run-form.ts:33), [onboarding.tsx:183](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/components/onboarding.tsx:183). | A failed request leaves text in the mounted form, but reloading to recover the connection or an OS tab eviction loses it. The request error tells the runner their input is still present; that promise does not survive a reload. | Persist draft edits with a bounded debounce and flush on field blur/visibility changes; do not rely on a last-second unload handler. Key drafts by account/epoch, run/workout and source revision. Recover a draft explicitly, and clear it only after a verified durable save or deliberate discard. Separate form-draft persistence from queued mutation persistence. |
| **P1 — No phone recording or background location architecture exists.** No native iOS/Android project, `watchPosition`, location stream, GPS filtering, sensor collection, running timer, recording state machine or active session table was found. The documented product is planning plus FIT/Intervals.icu delivery, [about/page.tsx:51](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/app/about/page.tsx:51). | Starting, tracking and finishing an offline marathon on the phone is not currently a supported journey. GPS drift, urban-canyon recovery and battery drain cannot honestly be graded from this app. A responsive web screen cannot substitute for a background recorder. | Decide whether native recording is in the product scope. If it is, build a native recording service with an explicit idle/acquiring/running/paused/recovering/finished state machine. On iOS use Core Location and its supported background activity/session APIs; on Android use a correctly declared location foreground service and visible notification. Ask for the minimum justified permissions at the point of use. Do not assume “Always” location is required for every foreground-started workout. [Apple background location](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background), [Android location guidance](https://developer.android.com/develop/sensors-and-location/location/battery/scenarios). |
| **P1 — There is no durable active-run checkpoint to recover at kilometre 15.** The existing recovery feature restores exported plan/journal data; it does not recover a recording session. The schema has plan JSON, revision JSON and run summaries, not active-session/sample records. Evidence: [db/schema.ts:8](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/db/schema.ts:8), [db/schema.ts:110](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/db/schema.ts:110). | If native recording were bolted onto the current React state model, process death could lose the run or corrupt elapsed time, distance and interval position. There is currently no phone-recorded run to recover at all. | Add a local SQLite session log with stable session UUID, append-only sample sequence, monotonic elapsed time, UTC timestamps, pause/resume events, interval position and upload watermarks. Commit bounded batches and checkpoint derived totals; rebuild from committed events on restart. Show a recoverable-session prompt and an explicit route gap. Distinguish OS termination from user force-quit; neither uninterrupted tracking nor reconstruction of unobserved locations can be promised. Test OOM/process termination during each state and while committing/syncing. |
| **P1 — Commercial billing is scaffolding, not an operational subscription system.** `/api/billing` always returns disabled; only sandbox Stripe keys are accepted. There is no public webhook consumer, billing table, customer portal flow, operational entitlement enforcement, paywall or StoreKit/Play Billing implementation. Evidence: [billing/route.ts:7](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/app/api/billing/route.ts:7), [billing.ts:35](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/lib/billing.ts:35). | The app cannot yet charge users, restore purchases, reconcile a cancellation/refund, explain an expired trial or reliably authorize a paid feature. There is no paywall load time to measure. This is an explicit preview limitation, not proof of broken current charging. | Build one server-owned entitlement model with provider/customer/subscription bindings, checkout intents and audited entitlement transitions. Gate paid server actions using that model. Use Stripe for the chosen web sales flow. For native store distribution, implement the appropriate StoreKit/Google Play purchase flows and verify transactions on the backend. Apple recommends signed transaction information/App Store Server API rather than starting a new integration on deprecated `verifyReceipt`; Google recommends purchase-token verification and acknowledgement. [Apple verification](https://developer.apple.com/documentation/storekit/validating-receipts-with-the-app-store), [Google verification](https://developer.android.com/google/play/billing/security). |
| **P1 — The billing reducer relies on infrastructure that has not been built.** Its comment requires a durable event inbox, serialized processing, CAS and a fresh provider read after acquiring a lease. The code stores only the last 100 event IDs in a record; no durable consumer enforces those requirements. Evidence: [billing.ts:179](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/lib/billing.ts:179), [billing.ts:207](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/lib/billing.ts:207). | Enabling the adapter directly could process duplicate deliveries twice or overwrite current entitlement from concurrent stale snapshots. Unit tests of the reducer do not prove webhook delivery reliability. | Receive verified raw webhook bodies into a durable inbox with a unique provider/event ID and acknowledge promptly. Process per subscription under a lease or compare-and-swap; refresh provider state inside that serialized operation. Use retries/backoff, dead-letter handling and reconciliation for missed events. Stripe explicitly does not guarantee event delivery order, so `event.created` must not be the authority. Test duplicate, delayed, out-of-order, concurrent, crash-after-insert and missing-notification paths. [Stripe webhooks](https://docs.stripe.com/webhooks). |
| **P1 — Trial conversion, payment failure and grace are not a complete entitlement policy.** `sandboxEntitled` recognizes only `active`/`trialing` before `periodEnd`; it has no grace window, provider-specific hold/refund rules, cancellation-effective timestamp, verification freshness or local entitlement lease. Checkout does not configure a trial. Evidence: [billing.ts:112](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/lib/billing.ts:112), [billing.ts:210](/Users/elijassohlstrom/Documents/Codex/2026-09-11/github-plugin-github-openai-curated-remote/work/stride/lib/billing.ts:210). | A paid release cannot clearly tell an eligible user whether access should continue after a failed renewal, during offline use or after cancelling auto-renew. Incorrectly treating every failed payment as immediate expiry creates avoidable lockouts. | Define provider-normalized states and effective access dates. Honor configured/store grace states, differentiate cancellation from expiration, and handle holds, refunds, revocation and recovery. Receive App Store notifications/Play RTDNs and reconcile with provider APIs. Use a bounded, account-bound cached entitlement for offline features, with explicit refresh and expiry rules; never interrupt an already-started recording. Trial eligibility, consent, conversion and no-payment-method outcomes need end-to-end sandbox tests. [Stripe subscription lifecycle](https://docs.stripe.com/billing/subscriptions/webhooks), [Google grace and hold states](https://developer.android.com/google/play/billing/lifecycle/subscriptions). |
| **P2 — GPS quality and battery budgets are unspecified because the recorder does not exist.** There is no Kalman filter, quality classifier, signal-gap policy or measurable sampling strategy. | Adding a filter alone can make a route look smoother while distorting corners, distance or instant pace. Conversely, high-rate sensors/network writes left active after finishing would waste energy. These are design risks to test, not measured present defects. | Retain raw and processed data. Before optional Kalman smoothing, reject stale/non-monotonic samples and implausible jumps using uncertainty, speed and acceleration checks. Exclude uncertain gaps from exact-distance claims, present degraded GPS status and keep elapsed time independent of GPS. Use fused platform location, adaptive accuracy/frequency and batched local writes; only activate accelerometer/gyro when needed. Limit map rendering and background network traffic. Stop sensors immediately at finish. Establish a device test matrix for 2/4/6-hour outings, locked screen, poor signal, music and low-power mode, and measure energy/thermal use instead of declaring a battery percentage from source inspection. [Apple energy guidance](https://developer.apple.com/documentation/xcode/accessing-the-device-s-location-efficiently), [Android battery guidance](https://developer.android.com/develop/sensors-and-location/location/battery). |
| **P2 — The future paywall needs an offline-safe product contract.** No premium UI currently exists, so placement, legibility, price availability and loading states are untested. | A network-dependent paywall at a workout start would turn the moment of highest intent into a failure. Stale cached prices can also mislead a user. | Let runners understand a sample plan/value before presenting the upgrade, make dismiss/restore/manage options clear, and avoid gating an ongoing run or access to existing personal records. Cache presentation assets and last-known descriptive product information; show purchase unavailability offline and revalidate live product/price/eligibility before purchase. Keep entitlement restoration separate from fresh checkout. Measure conversion and time-to-ready only once the real flow exists. |

The highest-value existing protections should be retained: server-owned account identity/epoch checks; plan compare-and-swap; a stable activation request ID; aborted/superseded journal-read protection; atomic publication of matching account/profile/state snapshots; provider-delivery receipts; tested sandbox Stripe signatures and account bindings. The absence of a durable offline journal does not mean the existing account recovery and concurrency controls are absent.

**Test evidence.** Ran the existing billing, client-session, journal-loading and recovery suites: **45 tests passed, 0 failed**. These are isolated logic tests, not live payment or device tests. A separate synthetic reproduction loaded the real API and storage code using the repository's in-memory SQLite/TypeScript VM harness. Sending the same manual `freeRun` payload twice, including `version: 0` and the same supplied `run.id`, returned:

```json
{"firstStatus":200,"retryStatus":200,"firstCount":1,"retryCount":2,"payloadIdentical":true}
```

The two records had different server-generated UUIDs. This is sufficient to prove the manual-create retry defect without touching a real journal. A network-failure integration test should model the first commit succeeding while its response is lost, then submit the same persisted mutation ID after reconnect.

The requested zero-cellular-marathon scenario is currently unsupported in Stride itself: the runner needs a separate watch/recording app; an already-delivered workout may remain available there subject to that device's behavior. Stride can import or log the result later. A browser restart can lose its current plan view and unsaved feedback. An OOM at kilometre 15 likewise cannot be tested as a Stride recording-recovery case until recording exists.
