# Backend, data integrity, privacy and integration audit

Reviewed 23 September 2026 against the current working tree. Read-only production-code review; no customer data, credentials or live provider accounts were accessed. Only this report was written. Local tests use isolated synthetic fixtures. These findings concern the existing web training journal; native activity recording is absent, so GPS ingestion and health-store recommendations describe missing capability rather than defects in a recorder that already exists.

Severity: **P0** = public-release blocker or prerequisite for the requested recording product; **P1** = serious reliability or integrity limitation; **P2** = material hardening. “Unverified” is explicitly not a reproduced exploit or measured outage.

| The Issue | The Impact | The Fix |
|---|---|---|
| **P0 · Deployment authentication trust is not established by application code.** `ownerId()` accepts `oai-authenticated-user-id` as the complete identity claim; there is no signature/session verification in the application ([server.ts](../../../lib/server.ts#L33)). Pages use the same claim. Hosting configuration only identifies project/database bindings; the current privacy page says Sites sign-in supplies identity ([privacy](../../../app/privacy/page.tsx#L38)). **Unverified boundary, not a demonstrated bypass.** | Every owner-scoped SQL predicate is only as trustworthy as this header. If a public/origin path accepts a caller-supplied identity claim, the otherwise careful database ownership checks would not protect journals. Unit tests inject these headers and cannot certify gateway behavior. | Before public access, verify that every route is behind the authenticated gateway, client-supplied identity headers are removed/replaced, direct origins are inaccessible, and logout/session-expiry behavior is consistent. Test two isolated accounts on the actual production ingress. If deployed outside that guarantee, verify signed sessions/tokens server-side and derive the owner exclusively from the verified subject. Preserve owner binding, origin validation and account epochs. |
| **P0 for a recorder · There is no granular activity schema.** D1 stores the complete plan as text, revision copies as text, and standalone run summaries as text ([schema](../../../db/schema.ts#L8), [run types](../../../lib/plan/types.ts#L258)). No tables or object manifests represent GPS points, heart-rate samples, elevation, laps, pause events, route segments or stream quality. | There is no path to record/recover/reanalyze a marathon, inspect GPS glitches, compute reliable splits, or compare planned intervals with actual execution. Appending time series to the existing plan blob would quickly reach its 1.5 MB cap. | Introduce an independent activity domain: immutable activity UUID; owner; start/end instants; original timezone/offset; local activity date; elapsed/moving time; source identities; status; quality flags; calculation version. Store append-only, checksummed sample chunks outside the plan snapshot, with an ordered manifest and indexed summary/lap tables. Preserve raw versus cleaned streams and explicit gaps. Keep planning history separate. |
| **P0 for promised platform parity · Apple HealthKit, Google Health Connect and direct Strava/Garmin adapters do not exist.** Current connection is a manually entered Intervals.icu personal API key; Garmin delivery goes through Intervals.icu and subsequent user verification ([connections](../../../app/api/connections/route.ts#L45), [setup guide](../../../components/watch-setup-guide.tsx#L18)). | A user expecting “connect my health data/watch” encounters another account, key handling and several external steps. Stride cannot claim automatic health-store sync or direct device integration. A successful provider receipt does not prove a watch received a workout. | Build narrowly scoped native health-store adapters and approved provider integrations with explicit per-provider status. Keep source record IDs, revisions, deletion tombstones, consent and cursors. Use authenticated OAuth flows where supported; serialize token refresh, encrypt tokens, handle revoked scopes, and queue imports. Health Connect needs persisted change tokens, interruption recovery and deduplication; Strava needs webhooks and application-wide quota coordination. Do not present planned integrations as available. |
| **P0 · Public privacy and support operations are explicitly unfinished.** The privacy page says operator identity, contact, jurisdiction, processing basis, retention and backup erasure still need establishing ([privacy](../../../app/privacy/page.tsx#L8), [backup lifecycle](../../../app/privacy/page.tsx#L55), [support](../../../app/privacy/page.tsx#L77)). | Public customers have no established operator/support path for sensitive training data or failed recovery. Application deletion is implemented, but infrastructure backup removal and downstream copies are separate obligations. | Complete the public notice, consent/data inventory, documented retention and deletion lifecycle, support ownership, incident response and restore drills. Verify actual provider contracts and hosting controls; obtain jurisdiction-appropriate review. Do not equate deletion of application rows with erasure of external copies. |
| **P1 · Impossible distance/time combinations pass validation.** `validateRun()` bounds minutes and kilometres independently, without a relationship check ([run-input](../../../lib/run-input.ts#L5)). Provider summary normalization also has no speed/plausibility cross-check ([provider activities](../../../lib/provider-activities.ts#L11)). **Reproduced:** 100 km in 1 minute and 2 minutes both pass the actual validator. Exactly 100 km in 2 seconds is rejected on save because durations below 1 minute are disallowed. | A corrupt provider summary or typo can contaminate training-history distance, weekly load and progression evidence despite every individual field being within allowed limits. Bounds alone are not data quality. | Add sport-aware cross-field plausibility validation and an explicit quarantine/review state. Preserve the raw source value with a reason; exclude suspect records from adaptive evidence until resolved. For future GPS streams, reject non-monotonic/duplicate timestamps and flag impossible speed/acceleration or poor accuracy before summing distance. Do not silently clip an implausible record into a plausible one. |
| **P1 · An edit rewrites and versions the entire journal, and state reads return the whole plan.** `saveState()` serializes all data, writes the full text, then copies it into revisions on every successful change ([server](../../../lib/server.ts#L194)); `/api/state` returns the entire plan, all standalone runs and delivery records ([state route](../../../app/api/state/route.ts#L4)). The explicit current-journal cap is 1,500,000 bytes; standalone data is capped at 500,000 bytes/4,000 runs ([standalone](../../../lib/standalone-runs.ts#L48)). | Work and transfer size grow with lifetime journal history, not with the small change a runner makes. A note edit can create another large full snapshot. Eventually a loyal user's valid new log is refused. JSON encoding itself is not the central problem. | Normalize run records and block revisions; use record-level mutation endpoints and paginated history; return mutation results/deltas with a revision cursor. Keep bounded snapshots plus compact audit events. Compress transport normally and measure actual payloads; use packed binary/Protobuf only for dense sensor chunks where measured benefit justifies complexity. |
| **P1 · Revision retention is unbounded.** The revisions table holds full snapshots by owner/version ([schema](../../../db/schema.ts#L15)); saves insert another copy ([server](../../../lib/server.ts#L234)). Normal reads show limited rows, but there is no routine compaction/retention job. Account deletion clears data, which is different from ongoing retention. | The 1.5 MB current-state cap does not cap total stored history. Repeated ordinary edits multiply storage/write cost and retain old sensitive notes indefinitely until account deletion. | Define a deliberate revision policy: short-term fine-grained undo, periodic compacted snapshots, a durable small audit trail, and lifecycle deletion consistent with the public notice. Test restore across compaction boundaries before enforcing retention. |
| **P1 · Weekend-scale capacity has not been demonstrated, and current work amplifies contention.** All users use the same `DB` binding; plan saves write full snapshots, revision rows and account counters. State reads parse whole histories; rate limits are also database writes ([server](../../../lib/server.ts#L131), [state](../../../app/api/state/route.ts#L7)). Provider delivery runs synchronously in the HTTP request. **Architecture risk, not an observed production outage.** | A finish-time burst can queue slow journal writes and provider calls. A global provider incident can occupy requests while users repeatedly retry. A large passing unit suite does not establish throughput. | Add durable import/delivery jobs with per-athlete serialization, unique job keys, bounded worker concurrency, backoff/jitter and dead-letter review; keep journal saves short. Load-test burst and sustained traffic with realistic journal sizes, latency percentiles, errors and provider throttling. Measure D1 before considering tenant partitioning/sharding. Cloudflare documents that one D1 database processes queries serially and can return overloaded errors when its queue fills. |
| **P1 · Provider synchronization is a user-driven request, not a durable background workflow.** Calls have a 20-second provider timeout ([server](../../../lib/server.ts#L418)); client requests have a 25-second timeout ([client](../../../lib/client-api.ts#L74)). Delivery uses a two-minute claim and reconciles ambiguous creates ([garmin](../../../lib/garmin.ts#L288), [unknown create](../../../lib/garmin.ts#L547)). No scheduler/outbox is registered in the current backend. | Wi-Fi → cellular → lost response leaves a user needing to reopen and check delivery. Closing the app does not guarantee a pending job will be retried later. Existing reconciliation protects against many duplicate uploads, but is not an eventual-delivery promise. | Persist an operation before dispatch, return an operation ID quickly, and let a durable worker reconcile/retry eligible operations. Surface queued/sending/provider-received/device-confirmed states independently. Preserve the current rule against blindly retrying an uncertain provider POST. Offline client commands need their own persistent outbox and stable IDs. |
| **P1 · Imported start instant and timezone are discarded.** Normalization exposes `startLocal`, `startUtc` and `timezone` ([provider](../../../lib/provider-activities.ts#L31)); saving only persists a date and summary ([plan route](../../../app/api/plan/route.ts#L509), [new record](../../../app/api/plan/route.ts#L576), [standalone](../../../lib/standalone-runs.ts#L28)). Stored run types have no actual start-time/zone fields ([types](../../../lib/plan/types.ts#L117), [extra run](../../../lib/plan/types.ts#L258)). | The original activity's instant, offset and time-of-day cannot be reconstructed after a flight, DST transition, same-day double or cross-provider import. Date-only historical entries themselves are stable; this is information loss rather than a demonstrated calendar-day jump. | Preserve `startedAtUtc`, `endedAtUtc`, source IANA zone and offset plus the activity-local date at ingestion. Display original activity-local time by default, optionally current-zone time. Keep scheduled training dates as date-only values; do not blindly convert them with the browser timezone. Test DST gaps/folds and date-line travel. |
| **P1 · Import deduplication does not model later provider updates/deletions or multiple providers.** Existing activity IDs are detected and cannot be imported twice ([plan](../../../app/api/plan/route.ts#L490)); namespaced IDs include the Intervals athlete and source activity ID ([provider](../../../lib/provider-activities.ts#L28)). There is no persisted upstream modification version, provenance graph, change cursor or tombstone. | A corrected upstream distance can remain stale in Stride. The same future activity arriving from a watch, health store and Strava would have different IDs and could count several times. Deleting or revoking upstream data is not automatically reconciled. | Model source links separately from the canonical activity, with unique provider/account/source IDs, upstream version/hash, sync cursor and tombstones. Preserve manual corrections separately from immutable source observations. Match likely cross-provider duplicates conservatively and let runners resolve uncertain matches. Implement explicit deletion and consent-revocation policy. |
| **P1 for social route features · No privacy-zone/redacted-route architecture exists.** There are no route coordinates or public activity shares in the present schema, so **no current home-location leak was established**. | Adding raw GPS recording or social sharing without a separate visibility/export layer would make home locations easy to expose through maps, downloads or previews. Removing just the first point is not adequate protection. | Keep raw routes private. Generate an independently redacted public route, clipping start/end areas and every passage through chosen privacy regions. Apply the same transformation to map tiles, thumbnails, downloads and public APIs. Default private; require a share preview and explicit audience selection. Avoid publishing exact activity-local start metadata alongside a redacted map unless intended. |
| **P2 · Security headers and key rotation are incomplete hardening.** CSP currently contains only `object-src`, `base-uri` and `form-action`; no `frame-ancestors` or nonce-based script policy ([config](../../../next.config.ts#L14)). Provider keys are correctly AES-GCM encrypted with a random IV, but the stored value has no key-version metadata ([server](../../../lib/server.ts#L280)). **No XSS or clickjacking exploit was tested.** | Framing protection is not enforced by the checked-in policy; script containment is limited. Rotating the sole encryption secret makes old connection records unreadable without a migration/fallback. | Add an appropriate `frame-ancestors` policy, introduce nonce/hash CSP in report-only mode first, and verify actual deployed headers. Version encrypted envelopes, keep a bounded old-key decrypt window, re-encrypt on read or via a controlled migration, and document emergency revocation. Keep credentials out of client storage and logs. |
| **P2 · Operational diagnosis is too coarse for a paid public product.** Unknown server errors log only a random ID, 500 status and time ([server](../../../lib/server.ts#L110)); user-facing provider errors often return without structured failure telemetry. Funnel counters reset daily and do not measure service reliability ([measurement](../../../lib/measurement.ts#L10)). | A support request cannot readily be tied to a failing subsystem, latency regression, D1 saturation or persistent import queue. Privacy-conscious logging is good, but omission of even safe categories prevents timely detection and remediation. | Emit redacted structured event names, handler/operation category, duration, outcome, retry count and provider status without raw payloads/notes/coordinates. Add alerts for write failures, queue age, reconciliation failures, 429 rates, D1 latency and account recovery. Establish error budgets and recovery ownership; verify redaction in tests. |

## Existing protections that must be retained

- Owner-scoped prepared queries, same-origin JSON write checks, request-body byte limits and non-cacheable API responses exist. Do not describe the API as having no authorization or basic validation.
- Plan writes have optimistic version checks; account ID/epoch fences protect against writes after restore, closure or sign-in changes. Batches couple state and revision writes.
- Provider import identity is rechecked across network calls and guarded at commit. Imported summaries are fetched from the connected provider rather than trusting client-supplied source data.
- Imports deduplicate by scoped provider IDs. Completed/extra run records are not blindly double-counted.
- Delivery claims serialize a workout's send, ambiguous creates remain ambiguous, and readback checks date, step termination, duration, intensity and targets. Provider receipt is distinct from manual device confirmation.
- Recovery export excludes connection credentials. Account deletion, restore previews, stale-write rejection and corruption checks have real implementations and tests.
- Calendar arithmetic uses date-only strings and UTC-noon helpers. Historical date display is explicitly UTC to avoid browser timezone shifts. The missing original timestamps should be fixed without undoing this correct scheduling design.

## Verification performed

- **131/131 existing focused tests passed**: activity status, account recovery, client sessions, imports, delivery policy, Intervals readback, operations and journal dates. Executed locally with synthetic test fixtures and no live provider calls.
- Direct production `validateRun` probe: 100 km / 2 seconds rejected; 100 km / 1 minute accepted; 100 km / 2 minutes accepted.
- Direct date-helper probe: the same stored `2026-09-20` renders `20 Sept`; `todayInZone` correctly distinguishes Dublin `2026-09-23` from Los Angeles `2026-09-22` at the same instant `2026-09-23T00:30Z`.
- No production authentication penetration test, provider certification, sustained load test, native sensor recording, or actual infrastructure backup restore was performed. Those cannot be inferred from these passing tests.

## Primary platform references checked

- [Cloudflare D1 limits and concurrency](https://developers.cloudflare.com/d1/platform/limits/) and [D1 overload diagnosis](https://developers.cloudflare.com/d1/observability/debug-d1/): one database executes queries serially; excessive queued work can overload it. This supports the need to measure the current workload, not a claim that D1 cannot support the product.
- [Android Health Connect synchronization](https://developer.android.com/health-and-fitness/health-connect/sync-data): interrupted sync, persisted tokens, deletion handling and deduplication are part of an actual adapter; unused change tokens expire.
- [Health Connect writes and metadata](https://developer.android.com/health-and-fitness/health-connect/write-data): client record identity/version and source metadata support safe updates; write activity data after completion or via a deferred job.
- [Strava rate limits](https://developers.strava.com/docs/rate-limits/) and [webhooks](https://developers.strava.com/docs/webhooks/): quotas are application-wide; provider change notifications avoid continuous per-user activity polling. Access and increased capacity require review.
