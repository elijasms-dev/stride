# Workout execution, targets and UX source audit

Reviewed 23 September 2026. Read-only production-code review; no application code or saved user data changed. Scope: workout execution, target calculations, delivery UX, onboarding, accessibility structure and client state. Browser observations belong to the companion main audit. Severity is conditional on the intended product: a missing phone recorder blocks positioning as a full run-tracking app, but does not prevent launching an honestly described training planner.

## Critical distinction

Stride currently authors training prescriptions, displays instructions, records manual/imported summaries, and exports workouts. Its Today CTA is **Open workout**, not **Start run** (`components/app/today-workout-card.tsx:149`). `components/workout-detail.tsx:147` renders the saved prescription and `:231` renders watch delivery. Source searches found no location tracking, live timer/interval state machine, audio playback/speech engine, motion-sensor integration, haptic dispatch or auto-pause implementation. These capabilities are **absent**, not implementations whose field accuracy was tested.

Measure actual power use before presenting a battery-life claim. Do not add accelerometer/gyro sampling simply because other running apps have it. |

## Positive controls that should survive the fixes

- Heart-rate alerts are deliberately omitted for short efforts, recoveries and hills, reducing pressure to chase delayed sensor readings (`lib/workout-targets.ts:203`). There is no automatic measured-HR zone model today; HR bands are supplied by the runner/coach.
- FIT creation is bounded and decodes its own bytes to verify durations and target values (`lib/fit.ts:148–269`). This is valuable serialization verification, not evidence of correct execution on every watch.
- Provider delivery and user confirmation are intentionally different states (`lib/watch-setup.ts:37`; `components/watch-setup-guide.tsx:129`). Keep that distinction.
- Date labels treat planned dates as calendar dates and use a pinned training timezone (`lib/plan/calendar.ts:22`, `:42`, `:54`; `components/app/use-app-navigation.ts:84`). A flight should not silently shift the plan date. The main audit covers imported activity timestamp provenance separately.
- Existing app shell has a skip link, focus-aware scrolling, semantic dialogs, labels, reduced-motion checks and adaptive navigation safe-area measurement. Do not describe accessibility as wholly absent.

## Executed verification

- **47/47 existing targeted tests passed**: workout targets, benchmark input, watch setup and Intervals readback. No provider credentials used and no outbound workout sent.
- Pure-function checks reproduced accepted cross-band inversions and benchmark-to-effort override behavior.
- Isolated `renderToStaticMarkup(ScheduleFields)` with a 10K finish-intent profile, established 45 km/week, five runs, familiar two quality sessions and explicit two workouts emitted selected **0 / All easy**, while `requestedQualityCount(profile)` returned **2**. Advanced fields emitted “no separate hard session is requested.” Automatic mode similarly resolved to **1** in the engine and displayed **0** in the UI.
- No physical run, audio-timing test, battery test, native screen-reader pass, watch model acceptance test or real sensor trace was conducted in this source audit. Those must remain release gates rather than being inferred from passing plan simulations.
